# UDP 短时回执丢失修复

## 原因与范围

现场抓包显示：导航源健康，但 UDP 请求序号出现缺口后，App 发出的 `routeActive` 反复为 false 并在约 3 秒后恢复。发送器原先每次收不到 ACK 都清空 owner 确认，重新执行首次交接的 3000 ms 等待；该等待期间强制 inactive。证据与采样限制见 [车端检查记录](../../openpilot-navassist-track-p0/docs/LANE_RADAR_CHAIN_AUDIT_20260922.md)。

本轮只修改现有 `HttpNavAssistV2Exporter`，不修改协议、车端、语音、灯光保持或选道阈值。

## 修复

- 只有已确认的同一 UDP exporter 才允许有界 ACK 短缺。确认有效期取现有 `config.validForMs`，生产默认 1200 ms；每个有效 ACK 更新确认时间，失败不更新时间。
- 在发送下一包前及处理失败后都检查确认年龄。达到有效期、时钟倒退、首次连接、exporter 替换或停止仍撤销；重新确认沿用既有 3000 ms 交接等待。HTTP 失败仍沿用立即撤销。
- 单次丢回执仍立即清空车辆反馈、待播报请求和完成回执。此次不允许语音失败绕过变道门槛。
- 导航源失效、停止、路线资格、司机接管、盲区和车端 TTL 均不改变。短时传输失败不会伪造新导航观测或新事件 ID。

## 验证与部署

Android 159 项测试通过、0 失败，APK 构建通过。新增检查覆盖有效期内单次丢包、到期边界、时钟倒退、发布线程暂停、连续丢包不续期、到期后重新等待完整 3 秒；原发送者替换串行交接与停止测试仍通过。

APK SHA256：`0f477595456cc410e042df4081985fa8e7324b159448cde473f5f22dfe6207aa`。候选归档 `D:/C3/.codex-tmp/nav-udp-owner-fix-20260922/`。

用户随后明确要求安装，实时核实 `started=false`、模型／控制／变道进程均停止后，先拉取原 APK 至归档目录 `before.apk`，再以 `adb install -r` 保留数据安装并启动。手机实际安装 APK 的 SHA256 与上述测试版本一致。

安装后 C3 收到新 Android session，序号从203增长至224，导航 realtime／routeActive=true、stale=false，车辆仍 offroad。随后30秒双向抓包得到140个请求、280个ACK，全部请求 routeActive=true；序号323→325、332→334、413→415出现三处缺口，后续有效状态均未中断。该自然通信窗口支持短缺不再触发3秒撤销的修复效果，不能证明所有网络场景或手机内部收包状态。持续断连／超时撤销由单测验证，本次未在人车通信上注入故障。

安装与抓包记录保存在上述归档目录，`verification-summary.json` 为摘要。未宣称修复实体灯光断续或完成自动变道道路验收；空邻道空间判定与局部目标全局否决的问题仍在。此次没有改车机代码、导航设置或重新启动车机。
