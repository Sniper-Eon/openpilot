## 城市 NOA 数据利用原则

城市 NOA 采用“最大化利用、分层融合、失效降级”的原则：凡是 C3 已有的感知、定位、雷达、驾驶状态、控制状态，以及已经完成语义验证的原车/车机报文，只要数据仍然新鲜、有效且通过合理性检查，就应优先复用和交叉验证，不重复造一套数据，也不无故丢弃可用信息。

- 高德负责路线意图和地图先验，包括推荐/避选车道、转向动作、道路属性及路线事件；它不代表车辆周围的物理现实。
- C3 感知与定位负责连续道路几何、车道边界、目标物、相对运动和自车定位；原车/车机报文负责车辆真实状态、驾驶员操作、盲区、雷达、车道位置和车辆侧许可。
- 安全和执行判断由 C3 结合实时状态与原车/车机反馈完成。任何单一导航、视觉或 CAN 信号都不能绕过已确认的实线/路缘、盲区危险、驾驶员接管和控制权限制；正常正许可的融合遵循[变道统一计划](../../C3_LANE_CHANGE_CONSOLIDATED_PLAN.md)后续确认的 OR 规则，不把单一来源的普通拒绝等同明确危险。
- 新接入报文必须先通过日志回放或实车对照确认语义，并具备新鲜度、有效位、范围、连续性、冲突处理和诊断；未知、过期、跳变或互相冲突时保守降级，不因“有这个报文”就猜测其含义。
- 同一事实存在多个来源时进行融合与一致性检查；来源失效时在安全边界内使用其余可靠来源降级运行，不能把缺失值解释成“允许”。

## 数据链路

以下是已实现的接口分工；受上述来源门控限制，当前车道数据链路尚未完整启用。

1. 高德导航 SDK 通过 `showLaneInfo` 提供各车道允许方向和推荐方向。
2. `NavigationRepository` 调用纯 `AmapLaneNormalizer` 将数据归一化成 `LaneState`（已完成 P1）。
3. 导航页用箭头显示全部车道，推荐车道以绿色强调，并提示左侧、右侧或多车道推荐。
4. NavAssist v3 快照继续把相同的车道索引、允许方向和推荐方向发送给 C3XL。
5. C3XL 根据实时视觉车道拓扑、相邻车道、车道线、原车 0x239/0x399、盲区、驾驶状态和速度判断是否请求转向灯及允许变道。

这种分工保留了参考工程的车道表达与展示设计。C3 仅在视觉可控车道数与高德车道数一致、视觉自车位于道路边缘且与原车 `0x239` 边缘位置一致时，将视觉索引作为高德车道索引；视觉位于中间时，即使数量相同也可能只是更宽道路的局部窗口，不认定为绝对第 N 道。原车已确认位于最左／最右，且该边缘车道就在推荐集合内时，即使视觉只覆盖局部窗口，也保持当前车道；中间位置不确定时，已有的路线边缘选道可在正常变道后借 `0x239` 确认边缘，不能单纯为了定位发起探测性变道。车道线、邻道、盲区和原车许可仍按 C3 原有控制门控处理。手机不直接发送车辆控制指令。模拟导航只显示车道引导，NavAssist v3 不会把模拟路线标记为控制有效。
# TesNav 原车车道反馈

TesNav 的高德车道箭头仅负责给出路线推荐方向。App 展示 C3 回传的原车相对位置与 OEM 许可，不自行解码 CAN，也不把 App 相机作为控制权威。是否实际允许变道，仍由 C3 结合视觉边界、盲区、控制权和执行状态统一判断；不能将 OEM 许可等同最终安全结论，也不能移除 C3 视觉实线/路缘否决。

- `0x239`：判断最左、中间、最右或单车道；连续三帧一致才更新（该报文末字节是滚动计数，不按校验和处理）。
- `0x399`：由 C3 处理已有方向许可与危险信息；原车正许可不代表完整安全门控。
- 已改为“原车报告左/右侧许可”“原车未报告许可”或“许可未知”，并注明“等待 C3 判断”；原车边缘位置不再代表路线已就位。本机反馈超过“配置发送间隔＋350 ms”（默认 550 ms）后退出有效展示，无新消息也会触发更新；回到前台或重新绑定时重新检查缓存年龄。该期限只衡量本机接收年龄，不证明 CAN 源新鲜度，真机调度与热点抖动仍待验证。

以上原始信号确认与时效由 C3 所在版本负责；App 当前只有 C3 有效位和本机接收时间，不能推导精确的 CAN 样本年龄。239 middle 也不能用于确定高德的绝对第 N 道。

## 高德推荐与当前路线避选

TesNav 同时解析新版 `frontLane` 和旧版 `getLaneTypeIdArray()`。旧版第二个类型字符为 `F`、新版前景值为 `255` 时，标记为“当前路线避选”；推荐车道显示为绿色，避选车道显示为红色“避”。`F/255` 只表示当前规划路线不选择该车道，不等同于法规禁行，也不能代替实线识别。自动超车不会覆盖正在生效的高德推荐或路线避选引导。

## 为什么看不到连续的车道级导航

当前使用的是高德公开 Android 导航 SDK `11.2.100`。公开 Java API 中只有 `AMapLaneInfo`：车道数量、各车道转向箭头和当前路线推荐箭头；它通过 `showLaneInfo` 在 SDK 认为需要显示车道引导时短时回调，并在通过提示区后调用 `hideLaneInfo`。它不是连续输出的 HD Map 车道中心线、车道边界类型或自车所在车道接口。

当前车道回调只有在路线 ID 关联成立时才导出。2026-09-25 本地修复使已通过路径 ID 校验的 `onNaviInfoUpdate` 确认当前路线，随后接收主辅路／高架、路线通知、下一动作这三项无路径 ID 回调；每次接收仍核对已接受路线、最近引导和引擎安装路径一致，重算期间拒收。主辅路监听器也随引擎代次注册和移除，旧引擎回调不再进入新会话。尚未部署或完成实车回调验证。

以下情况都可能没有 `showLaneInfo`：当前道路没有高德车道数据、尚未进入路口提示距离、模拟/实时导航未真正启动、路线未匹配，或者该路段只提供普通 TBT 引导。TesNav 在隐藏高德默认导航布局的同时显式调用 `setLaneInfoShow(true)`，避免依赖 SDK 的默认显示开关；同时会记录 `TesNav-AMap` 日志并在页面区分“尚未触发、空数据、已隐藏”，实车时可用：

```text
adb logcat -s TesNav-AMap:I
```

公开 SDK 包内虽包含车道级渲染资源，但公开 `AMapNaviPath`/`AMapNaviLink` 没有连续车道几何接口。实线、虚线、道路边缘仍由 C3XL 的 `laneTopologyStateSP` 判断，自车左/中/右位置及 OEM 许可由 0x239/0x399 补充。
